Domain 01 · ~20% of the exam

01
INFERENCE

Running inference on Token Factory. Connect an app, run chat completions, handle streams, prototype in the Playground, then choose models, parameters and batch for the workload.

Explained from the documentation

Connecting an application

  • Base URL: https://api.tokenfactory.nebius.com/v1/. Auth is an API key sent as a Bearer token; the docs read it from NEBIUS_API_KEY.
  • The API is OpenAI-compatible: use the official OpenAI Python/JS client and change only base_url, the key and the model name. Models use org/model naming, e.g. moonshotai/Kimi-K2.5.
  • The main endpoint is /v1/chat/completions. The migration page's own example swaps OpenAI's responses.create() for chat.completions.create(), so Chat Completions is the documented path (the API reference also lists a Create-a-response endpoint).
  • Model types: text-to-text, embedding, vision. Embeddings and rerank have their own endpoints.

Source: Quickstart · Switch to Token Factory

Model flavors, speed and quality

  • Two flavors: Base and Fast. Both deliver identical model outputs; they differ in token price, latency and applied optimizations. Use Fast by appending -fast to the model name.
  • Fast uses smaller batch sizes, more compute and techniques such as speculative decoding to cut latency.
  • Optimizations the docs list: KV cache, Paged Attention (fixed-size, non-contiguous, on-demand memory blocks), Flash Attention, quantization, continuous batching, context caching, speculative decoding (an auxiliary model pre-generates likely tokens, the main model verifies them).
  • Nebius says optimized models keep roughly 99% of the original model's quality. Performance depends on batch size, GPU type (L40, H100, H200, B200), GPU count and inference-time optimizations.
  • The API supports the full set of vLLM parameters; the Playground exposes the commonly used ones.

Source: Inference overview

Responses: finish reasons, usage and errors

  • finish_reason: stop (natural stop or stop sequence), length (hit max_tokens/max_completion_tokens), tool_calls, content_filter.
  • usage: prompt_tokens, completion_tokens, total_tokens, plus prompt_tokens_details.cached_tokens and completion_tokens_details.reasoning_tokens.
  • Errors: 400 bad request, 401 missing/invalid token, 402 budget exhausted, 403 no access, 404 model not found, 422 validation failed, 429 token quota exceeded, 500 internal, 503 unavailable, 529 overloaded.
  • The reference schema lists neither seed nor top_k; extra top-level properties are allowed and extra_body passes engine parameters through.

Source: Create chat completion

Playground

  • No-code web interface, opened from a model card's Go to playground. Add a system prompt and few-shot examples to show the output format.
  • Compare opens two chats side by side; Copy to right/left syncs parameters and system prompts, but syncing may be impossible if the two models have different parameter sets.
  • View code exports the setup (including the chat) for your app; Save preset stores it for reuse/sharing.
  • Model card fields: input and output price (USD per million tokens), tokens per second (approximate), Quality = MMLU score reported by the model provider. Extended parameters come from List models with verbose=true.
  • Playground can set the response format (JSON object / schema) and function-calling descriptions under Model Parameters.

Source: UI & Playground

Batch processing (tag: verify)

  • For high-volume, latency-tolerant work. Jobs are asynchronous and most finish within 24 hours (a target, not a guarantee).
  • Batch requests cost 50% less than regular calls to base models; the discount does not depend on the model.
  • Input is a JSONL file, one request per line, each with custom_id, url (/v1/chat/completions or /v1/embeddings) and body; one model ID per file. Reported limits: up to 5,000,000 requests and 10 GB. Upload with purpose="batch".
  • Batch does not draw from your per-model rate limits, and the rate-limits page points async workloads at the Batch API for that reason. Re-check the live page before the exam for exact limits.

Source: Batch inference (page returned 404 to my fetcher; figures below come from a search summary of the official page)

Public serverless vs dedicated (preview for Domain 4)

  • Public endpoints run on shared infrastructure; their Region shows Global and the processing region can change without notice. Region-specific base URLs can stop working.
  • Dedicated endpoints process in the region they were deployed to.

Tap a question to reveal the options marked and the reasoning. Say your answer out loud first.

01.01A team has working OpenAI SDK code. What is the minimum change to run it against Token Factory chat completions?
  1. AKeep everything and add a region header so requests are routed to Nebius.
  2. BSet base_url to https://api.tokenfactory.nebius.com/v1/, provide the Token Factory API key, and use an org/model model name.
  3. CConvert prompts to the Responses API, which is the only supported path.
  4. DInstall the Nebius proprietary SDK and rewrite the message schema.
Answer B

The API is OpenAI-compatible; the switch guide lists exactly three changes. Trap: the Responses-API-only option is wrong, because the migration page's own example moves from responses.create() to chat.completions.create(), so Chat Completions is the documented path.

01.02A chatbot must answer faster, but the product owner forbids any change in answer quality. Which action fits?
  1. ASet n=2 and keep the quicker answer.
  2. BLower max_tokens to 64.
  3. CAppend -fast to the model name.
  4. DSwitch to a smaller quantized model.
Answer C

Base and Fast flavors return identical outputs; Fast trades price for lower latency (smaller batches, more compute, speculative decoding). Switching to a smaller model changes the outputs, n=2 multiplies cost, and a tiny max_tokens truncates answers.

01.03You stream a completion and need token counts for cost tracking. What is correct?
  1. AStreaming never returns usage, so tokens must be estimated locally.
  2. BUsage is only available in response headers.
  3. Cusage is attached to every chunk by default.
  4. DSet stream_options to {"include_usage": true}; usage arrives in the final chunk, which may have an empty choices array.
Answer D

Streams end with data: [DONE]; usage is null on every chunk except the final one when include_usage is true. Code that reads chunk.choices[0] on every chunk can crash on that last chunk.

01.04A JSON-extraction call returns truncated, unparseable JSON with finish_reason: "length". What happened?
  1. AThe output hit max_tokens / max_completion_tokens.
  2. BA stop sequence was matched.
  3. CThe model proposed a tool call.
  4. DA content filter removed part of the answer.
Answer A

length means the token cap was reached. Remember prompt tokens plus max_tokens cannot exceed the context length, and max_tokens defaults to 8192. content_filter, tool_calls and stop are the other values.

01.05A request that returns the top-5 alternative tokens fails validation. Which request is invalid?
  1. Astop with four sequences.
  2. Btop_logprobs: 5 with logprobs left unset or false.
  3. Ctemperature: 2.
  4. Dn: 1.
Answer B

top_logprobs requires logprobs: true. Four stop sequences is the maximum allowed, temperature runs 0–2, and n runs 1–128.

01.06A classification service must give near-identical answers on repeated calls. Which configuration is best aligned with the docs?
  1. An: 10 and pick the most common label.
  2. Btemperature 1.5 and top_p 0.3, both tuned.
  3. CA low temperature (e.g. 0) and leave top_p alone.
  4. Dpresence_penalty: 2.
Answer C

Lower temperature means less randomness, and the docs advise altering temperature or top_p, not both. Note seed is not listed in the chat-completions schema, so do not promise bit-for-bit reproducibility.

01.07Nightly, 2 million support tickets must be classified by morning, cost matters and nobody waits on results. Best choice?
  1. AThe Playground's Compare mode.
  2. BA dedicated endpoint with max replicas.
  3. CStreaming with maximum concurrency on the Fast flavor.
  4. DBatch processing with a JSONL input file.
Answer D

Batch is built for high-volume, latency-tolerant jobs: asynchronous, ~50% cheaper, typically done within 24 hours, and it avoids per-model rate limits. Fast costs more and would hit 429s at that concurrency.

01.08Which batch input line shape matches the documented format?
  1. AJSONL where each line has custom_id, url (/v1/chat/completions or /v1/embeddings) and body with the model ID.
  2. BParquet uploaded with purpose="fine-tune".
  3. CA CSV with a prompt column.
  4. DA single JSON array holding every request.
Answer A

One request per line, one model per file, upload purpose batch. (Tagged verify: confirm on the live batch page.)

01.09A colleague picks a model for a legal-review assistant purely because its model card shows the highest Quality value. What should you say?
  1. AQuality is Nebius's benchmark on your own data, so it is decisive.
  2. BQuality is the MMLU score reported by the provider, a generic benchmark; validate on your own task, and weigh price, speed and latency too.
  3. CQuality is an SLA guarantee for output correctness.
  4. DQuality is a latency measure.
Answer B

Card fields: input/output price per million tokens, approximate tokens per second, and MMLU as reported by the model provider. Model choice is a cost/latency/quality trade-off, evaluated on your workload.

01.10A team hardcodes the region-specific URL api.tokenfactory.us-central1.nebius.com for a public model in production. What is the risk?
  1. AThe key will be revoked after 30 days.
  2. BNo risk; public endpoints are pinned to that region.
  3. CPublic endpoints are "Global": the processing region may change without notice and region-specific base URLs can stop working. Use a dedicated endpoint for a fixed region.
  4. DRegion URLs are only for batch.
Answer C

Nebius gives no regional guarantee for public serverless endpoints; they suit testing and non-critical work. Dedicated endpoints are the region-bound option.

01.11Requests suddenly return HTTP 402. What does it mean and what do you do?
  1. ARate limit hit: back off using Retry-After.
  2. BValidation failed: fix the JSON body.
  3. CModel not found: check the name.
  4. DBudget exhausted: fix billing/top up.
Answer D

402 = budget exhausted. 429 = quota exceeded (retry later), 404 = model not found, 422 = validation. Mixing up 402 and 429 sends you to the wrong fix.

01.12Which statement about speculative decoding is correct?
  1. AAn auxiliary model pre-generates likely tokens and the main model verifies them.
  2. BIt prunes layers and reduces quality by ~30%.
  3. CIt requires customers to fine-tune a drafter first.
  4. DIt stores final answers across customers to return instantly.
Answer A

That is how the docs describe it. The Fast flavor uses it, and a custom speculator is optional (a Data Lab / post-training feature).

01.13A reasoning model returns an empty content with finish_reason: "length". Most likely cause and fix?
  1. AThe stop list is too long; remove entries.
  2. BReasoning tokens consumed the budget; raise max_completion_tokens (visible + reasoning) or lower reasoning_effort.
  3. CStreaming is disabled; enable it.
  4. Dn is greater than 1; set it to 128.
Answer B

max_completion_tokens bounds visible plus reasoning tokens, and usage.completion_tokens_details.reasoning_tokens shows how many were spent thinking.

01.14In Playground Compare mode you click Copy to right but parameters do not fully transfer. Why?
  1. APresets must be saved first.
  2. BCompare mode only works for embeddings.
  3. CThe two models expose different sets of parameters, so synchronization may not be possible.
  4. DCompare mode never syncs anything.
Answer C

Straight from the Playground docs. Closing one chat returns to single-model mode and keeps that chat's setup and history.

Domain 02 · ~35% of the exam

02
AGENTS

Building Agentic AI. The biggest domain: structured outputs, the agent loop with memory, Tavily and MCP tools, then reasoning/error recovery, evaluation and guardrails.

Explained from the documentation

Function calling: the loop

  • The model never executes a function. It returns tool_calls in OpenAI format; your code parses and runs them.
  • Flow: (1) define tools with JSON Schema (type: "function", function.name, description, parameters); (2) the model replies or proposes a call; (3) you run it and send back a message with role: "tool", the matching tool_call_id and name, then the model uses the result or calls another tool.
  • You must append the assistant message that contains the tool_calls before the tool results.
  • function.arguments is a JSON string; parse it (json.loads).
  • tool_choice: auto (default behavior), none, required, or a named function {"type":"function","function":{"name":...}}. Forcing a named function means the model cannot answer conversationally in that request.
  • Tool-calling training data and live tool schemas should match (see Domain 3).

Source: Function calling & tools

Structured, schema-constrained output

  • response_format: {"type": "json_schema", ...} follows your schema (JSON Schema spec; wrapper has name, schema, strict). The docs advise it whenever you need a strict structure.
  • {"type": "json_object"} guarantees valid JSON only; the model chooses the keys. You must tell the model to produce JSON in a system/user prompt.
  • Best practice: give the schema in both the prompt and response_format. Use Pydantic model_json_schema() in Python or zodResponseFormat in JS.
  • Not every model supports structured output; look for the JSON mode tag on the model card and compare models.
  • Check message.refusal first; if empty, parse message.content inside try/except.

Source: Structured output & JSON

Tavily: the five capabilities

  • Search (find sources when URLs are unknown, default start) · Extract (full content from URLs you have) · Map (site structure, URLs only) · Crawl (read many pages; Map + Extract) · Research (cited multi-source synthesis).
  • Common pattern: Search → Extract. Escalate from Search to Map/Crawl/Extract once you have a target site or URLs. Use Search for raw material you process yourself; use Research for a finished cited answer.
  • Search search_depth: ultra-fast (lowest latency, page summaries) · fast · basic (default, high relevance, 1 credit) · advanced (best relevance, broadest, 2 credits).
  • Other Search params: max_results (default 5; too high can lower quality), chunks_per_source, include_domains (hard filter; include_domains_mode: "prefer" widens), exclude_domains, topic: "news", time_range, start_date/end_date, include_raw_content, include_answer (use sparingly and verify), exact_match, auto_parameters (may pick advanced = 2 credits, so set search_depth yourself to control cost).
  • Keep queries under 1,500 characters and split multi-topic questions into focused searches. Score filtering (e.g. score > 0.7) is up to you.
  • Pass a consistent session_id across related calls; pass a stable human_id per end user when one key serves many users (Tavily hashes it).

Source: Tavily for agents · Search best practices

MCP: connecting agents to external tools

  • MCP (Model Context Protocol) is the standard way to expose tools to agents. Tavily's remote server is https://mcp.tavily.com/mcp/; its MCP page lists the tools tavily-search and tavily-extract.
  • Auth options: API key in the URL query (?tavilyApiKey=), in the Authorization header, or OAuth. Local server: npx -y tavily-mcp, Node 20+, key in TAVILY_API_KEY (prefix tvly-).
  • DEFAULT_PARAMETERS (header on remote, env var on local) sets default search params. X-Session-Id/X-Human-Id attribute usage.
  • Choosing a connection: SDK/API for production backends; MCP for shared team/org access; CLI + Skills for one developer's local session.

Source: Tavily MCP · Docs MCP

Agent loop, memory, evaluation, guardrails (concept tag)

  • Agent loop = model call → tool calls → results appended → repeat until the model answers or a stop condition triggers. Academy Module 1 builds and evaluates a simple tool loop and measures performance and cost.
  • Short-term memory = the running messages history inside the context window (trim/summarize when it grows). Long-term memory = an external store retrieved on demand across sessions. A larger max_tokens does not create memory. (General practice; the exam guide names the skill but the docs give no spec.)
  • Error recovery: return tool errors to the model as a tool message so it can adjust, cap retries, and use exponential backoff for rate limits.
  • Guardrails, approvals, cost budgets: iteration cap, token/credit budget, allow-lists of tools, human approval before irreversible actions, validated structured outputs.
  • Evaluation (Academy Module 4: why/what to evaluate, metrics and golden data): keep a fixed golden dataset, re-run after every prompt/model change, score factuality, citation accuracy, coverage, cost and latency; an LLM judge supplements but does not replace human-verified references.
  • Deep agents / sub-agents (Module 3): an orchestrator delegates sub-tasks to sub-agents with their own context and returns condensed results, keeping the orchestrator's context small.

Source: Nebius Academy: Agentic AI

Domain 03 · ~20% of the exam

03
CUSTOMIZE

Customizing a model with your own data. Prepare datasets, run fine-tuning in Data Lab, deploy and call the result, and know when prompting, RAG or fine-tuning (LoRA, full SFT, distillation) is the right tool.

Explained from the documentation

Choosing prompting vs RAG vs fine-tuning (concept tag)

  • Prompting first: cheapest and fastest to iterate; use few-shot examples and structured output.
  • RAG / search tools when knowledge is large, private or changes often and answers need grounding/citations. Fine-tuning does not reliably teach fresh facts.
  • Fine-tuning (SFT) for consistent style, format or behavior on a narrow, repeated task when you have quality examples. The docs say SFT gives tighter control and can lower inference cost and latency (shorter prompts) and trains on large datasets without prompt-length limits.
  • Combine them: fine-tune for behavior, RAG for facts.

Source: Post-training overview

Datasets

  • All fine-tuning datasets are JSONL, one example per line. Four types: conversational, instruction, text, pretokenized.
  • Conversational: {"messages": [...]}; the last message should be from assistant. Optional tools for tool-calling data: assistant turns hold tool_calls (arguments as a JSON string), results use role: "tool" with tool_call_id; the final message must be natural-language assistant text, not a tool call.
  • Instruction: {"prompt": ..., "completion": ...}. Text: {"text": ...}.
  • Pretokenized: input_ids (required), optional labels (-100 masks loss), optional attention_mask. All token IDs must come from the model's default tokenizer vocabulary.
  • Size limits: 50 GB per file via Data Lab, 20 GB via the Files API. Files API upload uses purpose="fine-tune".
  • Hold out validation data: the docs suggest an 80–90% train / 10–20% validation split.
  • Data Lab dataset sources: uploaded, S3-connected, imported inference logs, derived (SQL-filtered). JSONL works for upload and S3; Parquet only via S3 connection. Large uploads use multipart.

Job lifecycle, metrics, checkpoints

  • Create job needs model and training_file; optional validation_file, suffix, seed, integrations (Weights & Biases; Hugging Face output repo).
  • Status path: validating_files → queued → running → succeeded / failed (cancelled also terminal in the Python loop). Poll at most every ~15 s. Transient 5xx errors can be retried.
  • Metrics per checkpoint: train_loss and valid_loss. Checkpoints are saved per step (often once per epoch) with a fine_tuned_model_checkpoint name like ft:<base-model>-<date>:.... Use the latest checkpoint unless you have a reason not to; download files via the Files API.
  • Interpreting results (concept): train loss falling while validation loss rises or plateaus = overfitting → fewer epochs, more/cleaner data, lower learning rate, LoRA. Both high = underfitting or bad data.
  • Packing: samples are never truncated; attention is masked across packed segments. Pretokenized + packing needs all-1 attention masks. Some large MoE models require packing.

Source: Supervised fine-tuning

LoRA vs full SFT vs distillation vs other methods

  • lora: true trains only adapter weights and freezes the base; lora: false updates all weights (more compute/VRAM, bigger behavior shift).
  • The models page lists 49 base models; six are full-fine-tuning only (no LoRA): DeepSeek-V3-0324, DeepSeek-V4-Flash, Gemma 4 (E2B/E4B/31B) and Qwen3.5/3.6-27B. Others (gpt-oss, Qwen3, Qwen2.5, Llama) support both. Meta Llama models are deployable only through dedicated endpoints. Context options: 8k–128k, default 8192.
  • Distillation (concept + docs hints): use a strong teacher model's outputs (the store request flag and Data Lab inference logs support collecting them) to train a smaller student for lower cost/latency on a narrow task.
  • Custom speculator: trains a speculative-decoding drafter for your base model. Pretokenized data only; method.type="spec-draft"; architectures eagle3 (Token Factory only) or eagle3_original (portable to vLLM).
  • Reinforcement fine-tuning is upcoming via limited professional service; long-context SFT is supported for full weights or LoRA. The docs I read do not cover DPO.

Source: Models for fine-tuning · Data Lab fine-tuning

Data Lab and deployment

  • Data Lab = unified workspace for inference logs, datasets, batch outputs and fine-tuning artifacts. You can view/filter/export chat-completion logs, build datasets with SQL queries, and reuse them for batch inference and fine-tuning. Datasets are versioned for reproducibility.
  • Logs are collected automatically unless Zero Data Retention is on; ZDR requests cannot be imported.
  • Deploying fine-tuned or custom weights: dedicated endpoints support custom weights for eligible models, but the custom-weights page calls the feature beta, on request via Support. I could not read the separate fine-tuned-model deployment guide, so confirm the exact calling steps in the docs.

Explained from the documentation

Rate limits and scaling

  • Two limit types: RPM and TPM. Exceeding returns HTTP 429 with a Retry-After header (seconds).
  • Dynamic scaling in rolling 15-minute windows: average usage ≥ 80% of the limit → next window's limit ×1.2; ≤ 50% → ÷1.5. Hard ceiling 20× the base; beyond that you need Enterprise.
  • Worked example (60 RPM / 400k TPM baseline): +15 min 72 RPM, +30 min 86, +1 h 124, +2 h 258 (scale factors 1.2, 1.44, 2.07, 4.30).
  • Over-limit requests may succeed at lower priority and include x-ratelimit-over-limit: yes: an early warning before throttling.
  • Headers: x-ratelimit-limit-/remaining-/reset- × requests/tokens, x-ratelimit-dynamic-scale-, x-ratelimit-dynamic-period-remaining, x-ratelimit-dynamic-period-usage-. Remaining tokens replenish continuously.
  • Remedies: let limits grow organically, use the Batch API for async work, or go Enterprise (dedicated capacity, SLA, no soft caps).
  • Client-side backoff (general practice): honor Retry-After, otherwise exponential backoff with jitter, cap retries and concurrency.

Sizing rules for dedicated endpoints

  • GPU type and gpu_count set per-replica performance; replica count sets concurrency/availability. Start with one replica on the smallest GPU that meets baseline needs, then add autoscaling.
  • If latency is too high or replicas saturate, scale up GPU type / GPUs per replica first. Adding replicas raises concurrency but does not fix high per-request latency.
  • min_replicas = what you always need (reserved, non-preemptible while active); max_replicas = what you may need at peak, limited by available capacity.
  • Stopping an endpoint releases capacity; after restarts, incidents or maintenance the same GPUs are not guaranteed (status can be Starting / Not ready or Partially ready). Guaranteed capacity needs a reservation via Sales. Self-service dedicated endpoints have no formal SLA; ~99.9% monthly success is a historical figure, not a commitment.
  • Match the traffic shape: steady → higher min_replicas; spiky/unpredictable → low min, higher max; batch/internal → low min, accept warm-up; async bulk → Batch API.

Source: Best practices

API keys and secrets

  • Token Factory keys are created in the console; resources, including API keys, live inside projects within an organization. Store the key in an environment variable such as NEBIUS_API_KEY or a secrets manager. Never hardcode it or ship it in client-side code.
  • Leaked key (committed to a public repo, screenshot, client code): revoke it immediately, generate a replacement, update every environment variable/secret/app.
  • Rotate periodically (Tavily's page gives 90 days as an example). Zero-downtime rotation: create the new key while the old stays active, deploy, confirm it works, then delete the old one.
  • Team access: Organization Groups and Project Groups control access; SSO is available. Observability: org admins see all projects, project admins/members see their own, billing managers none.

Source: Tavily API key management · Orgs & projects · Quickstart

Retention, deletion and Zero Data Retention

  • Default: inputs/outputs are retained to support speculative decoding (on by default) and used for no other purpose. Inference logs are kept for Data Lab unless ZDR is enabled.
  • ZDR is enabled in the account profile at organization level (all projects/endpoints): inputs/outputs are not stored after processing, speculative decoding is disabled, and it may affect inference speed.
  • Nebius states it does not use customer content to train or improve any models, with or without ZDR. Customers own inputs, datasets, fine-tuned/distilled models and outputs.
  • At termination the customer chooses deletion or return of personal data. Deleting a project removes its observability data (no retention period is specified). The DPA is part of the Terms of Service; Nebius is a Data Processor.
  • For sensitive data (health, biometrics) the guide recommends ZDR + a dedicated endpoint.
